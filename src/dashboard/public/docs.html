Technical reference

How the agent works

A continuous LinkedIn daemon — not cron jobs. One action at a time, human-like delays, warm outreach sequences, network nurture, and a full SQLite audit trail.

Overview

The agent researches ICP-aligned people and posts via Unipile, engages (like / comment / view), sends connection invites only after a warm-up sequence, and publishes thought-leadership posts on Tue / Thu / Fri. Every mutating call goes through a rate limiter with daily quotas, burst pauses, and backoff.

No OS crons. Scheduling is an in-process loop that sleeps until the next opportunity. Working hours (Mon–Fri 08:00–19:00 local) gate all LinkedIn actions.

Daemon loop

On start: load env, write PID, reset burst counter, snapshot own profile. Then loop forever until halted or SIGTERM. 

flowchart TD
  Start([startDaemon]) --> Profile[fetchAndRecordProfile]
  Profile --> Loop{shutting down?}
  Loop -->|yes| Exit([exit])
  Loop -->|no| HB[writeHeartbeat]
  HB --> Halt{halted?}
  Halt -->|yes| Exit
  Halt -->|no| Pause{PAUSED?}
  Pause -->|yes| S60[sleep 60s]
  S60 --> Loop
  Pause -->|no| Hours{working hours?}
  Hours -->|no| SleepOff[sleep until next window]
  SleepOff --> Loop
  Hours -->|yes| Next[getNextScheduledAction]
  Next --> Idle{type = idle?}
  Idle -->|yes| S60
  Idle -->|no| Exec[executeAction]
  Exec --> Delay[human delay / burst via rate limiter]
  Delay --> Loop
  • Idle sleep — 60s when paused, no work, or quotas exhausted
  • Off-hours sleep — until next weekday morning (or 1h recheck on weekends)
  • Graceful stop — SIGTERM/SIGINT waits for the in-flight action, then clears PID
  • Halt — account restricted / disconnected stops the loop permanently until cleared

Schedule & windows

There are no cron expressions. Behavior is driven by calendar day, local hour, and quota state. The scheduler evaluates priorities in order:

  1. 1 Off hours → idle
  2. 2 Monday + quota → profile_audit
  3. 3 Tue / Thu / Fri + quota → create_post (beats engagement)
  4. 4 Stale invite withdrawal when due
  5. 5 Connection sync when due (randomized, no engagement quota)
  6. 6 Weighted candidates for current time window (or post-boost weights)
  7. 7 No candidates → research if search allowed, else idle
  8. 8 8% browse pause (skipped while post-boost is active)

Invite readiness rules
  • Post-sourced: must have commented and viewed
  • Search-sourced: must have viewed (no cold invite without a view)
  • Comment-sourced: own-post commenters need a profile view only

Network nurture

Alongside cold ICP outreach, the agent occasionally engages first-degree connections so LinkedIn activity looks more human. Nurture likes/comments share daily like/comment quotas but never advance the invite sequence. 

flowchart LR
  Sync[sync_connections] --> Conn[(connections table)]
  Conn -->|recent accepts| Pref[priority boost]
  Research[research network_distance=1] --> NPost[nurture post targets]
  Pref --> Pick[occasional like/comment]
  NPost --> Pick
  Pick --> Cool[per-connection cooldown]
  Cool --> Done[engaged, no invite stage]
Sync safety
  • Initial full relation backfill once, then first-page refreshes only
  • Max 3 syncs/day after backfill, spaced randomly 3–8 hours apart
  • Accepts inferred by correlating new relations with prior successful invites
  • sync_connections does not consume engagement quotas
  • In DRY_RUN, sync schedules state but skips Unipile API calls

Actions

Each action is a single LinkedIn verb. Mutating engagement calls run through executeWithRateLimit. Connection sync is quota-free.

ICP filter highlights

  • Exclude recruiters, coaches, spam title patterns
  • Exclude India / South Asia locations; prefer US, Europe, UK, Canada, AU, RU
  • People must match include title patterns
  • Posts: unless <6h old, need reactions + 2×comments ≥ 5
  • Keep discoveries with relevance score ≥ 75; engage preferred ≥ 80
  • Nurture network posts skip ICP/AI and use fixed relevance 88

Em-dash publishing gate

Content containing em/en dashes is blocked at three layers before any Unipile write: safety filter, rate limiter (contains_em_dash), and assertPublishableContent in the Unipile client.

Rate limits

First 14 days use ramp-up bases × 0.5. Afterward, steady caps apply. canAct checks: halt → pause → working hours → backoff → daily quota.
